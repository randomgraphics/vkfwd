# vkfwd ferry

`ferry` is the mechanical per-API-call forwarding implementation. It owns the
current Vulkan layer, generated command model, generated structure pack/unpack
code, transport contracts, receiver/replay scaffolding, generator scripts, and
internal tests for this approach.

All implementation-specific logic stays here for now: loader-chain setup,
global/instance/device dispatch tables, layer hooks, generated interceptors,
schema-versioned command chunks, copied parameter storage, transport-session
policy, and receiver replay helpers. Common code should move out only after
another implementation has the same invariants.

## Layout

- `core/`: shared wire-format, generated dispatch-table metadata, and
  serialization code linked by the forwarder and receiver. See `core/README.md`
  before changing protocol, stream, transport, or generated pack/unpack behavior.
- `forwarder/`: Vulkan loader-facing layer entry points and generated wrappers
  that pack source calls into per-thread request blobs. See
  `forwarder/README.md` before changing layer lookup, dispatch tables, or flush
  behavior.
- `test/`: in-process ferry tests and loopback transport helpers that bind the
  real forwarder to receiver replay without leaving the process.
- `receiver/`: replay-side scaffolding. It will own destination dispatch,
  source-to-destination handle maps, replay ordering, and copied command
  lifetimes as the receiver becomes complete.
- `script/generator/`: Vulkan XML driven code generation. Generated files should
  be regenerated from here instead of edited by hand.

## Current Generated Slice

The current generated command slice is intentionally small, but now includes
the loader-global enumeration calls needed by basic instance bring-up:
`vkEnumerateInstanceVersion`, `vkEnumerateInstanceLayerProperties`,
`vkEnumerateInstanceExtensionProperties`, `vkCreateInstance`,
`vkDestroyInstance`, `vkCreateDevice`, and `vkDestroyDevice`.

The generated forwarder body shape is:

1. optional manual pre-pack hook
2. construct generated `Command::Parameters`
3. pack into this thread's `Forwarder::request_stream()`
4. for response-bearing commands, flush the request stream through the transport
   session
5. unpack the response stream and copy output parameters back to the caller
6. optional manual post-response hook

Commands without return values or output parameters are usually deferrable: they
append a command chunk to the thread-local request stream and rely on a later
response-bearing command, or an explicit test flush, to send that stream to the
transport session. `vkDestroyInstance` is the lifecycle exception and flushes
immediately so receiver-side deferred work observes instance teardown in order.

## Design Bias

The implementation bias is to generate most Vulkan API handling and submit
intercepted accumulated request streams to a `TransportSession`. Each request
stream begins with a fixed `RequestStreamHeader` carrying the source
stream id, so per-stream routing is part of the byte stream instead of a
separate transport object. The forwarder
does not call a local Vulkan driver and does not keep per-instance or per-device
dispatch state beyond shared generated dispatch tables. Local replay, remote
transport, response synthesis, source-to-receiver handle mapping, and
synchronization policy belong below the transport/receiver boundary.

## Generated Code Policy

Files under `core/generated/` and `forwarder/generated/` are generated by
`src/vkfwd/ferry/script/generator/vulkan_metadata.py`. Do not edit generated
command, structure, dispatch-table, or generated-test files by hand. Update the
generator and regenerate instead.

Manual code belongs outside generated directories, except for generated tests
that are intentionally emitted to keep pack/unpack behavior covered as the
generated surface grows.

## Generator Grouping Policy

The generator must scale toward the full Vulkan API without producing one
compiled source file per command. Keep typed command headers per command while
grouping compiled implementation and test sources by API domain. Per-command
headers preserve useful `Command::Parameters` and `Command::Response` type
boundaries; grouped `.cpp` files keep full-API builds and reviews manageable.

Target group size is 25-60 commands. Lifecycle or loader-global groups may be
smaller when their dispatch or replay semantics are special. Large domains must
split before exceeding roughly 75 commands.

Preferred command implementation groups are:

- `global_instance`: loader-global calls, instance creation, and instance
  enumeration, about 15-25 APIs.
- `physical_device`: physical-device properties, features, formats, memory, and
  capability queries, about 40-60 APIs.
- `device_lifecycle`: device creation/destruction, queues, and device-idle
  commands, about 10-20 APIs.
- `memory_buffer`: memory allocation/mapping/binding and buffer commands, about
  30-45 APIs.
- `image_imageview`: image, image-view, sparse image, and image-memory
  commands, about 50-70 APIs.
- `shader_pipeline_layout`: shader modules, pipeline layouts, pipeline caches,
  and pipeline creation, about 40-60 APIs.
- `renderpass_framebuffer`: render-pass, framebuffer, and dynamic-rendering
  setup commands, about 25-40 APIs.
- `descriptor`: descriptor set layouts, pools, allocation, updates, and related
  descriptor operations, about 35-55 APIs.
- `command_pool_buffer`: command pool and command-buffer lifecycle commands,
  about 30-50 APIs.
- `cmd_draw_dispatch`: draw, dispatch, bind, push, and indirect command-buffer
  recording commands, about 50-70 APIs.
- `cmd_copy_blit_resolve`: copy, blit, clear, fill, resolve, and transfer
  recording commands, about 50-70 APIs.
- `cmd_barrier_sync`: barriers, events, waits, pipeline barriers, and layout
  transition recording commands, about 40-60 APIs.
- `sync_objects`: fences, semaphores, events, timeline sync, and wait/signal
  operations, about 35-55 APIs.
- `query_timestamp`: query pools, timestamps, counters, and calibrated timing,
  about 25-40 APIs.
- `sampler`: sampler and sampler-ycbcr-conversion commands, about 10-20 APIs.
- `surface_swapchain`: surface and swapchain commands, about 40-60 APIs.
- `debug_tooling`: debug utils, markers, labels, and object naming, about
  20-40 APIs.
- `extensions_misc`: extension-family overflow groups, split by related
  extension families and kept around 30-60 APIs where possible.

Per-command metadata JSON should not be generated by default once a command is
included in the grouped full manifest. Store command metadata in
`generated/vulkan_manifest.json`; add inspection tooling instead of emitting
hundreds of small metadata files.

Generated structure serializers have their own grouping policy. Structure groups
should follow pointer-ownership shape and Vulkan object domain, not the exact
command groups above. A structure group should collect related structs that share
nested array rules, pNext contracts, handle references, or replay assumptions,
because those are the invariants reviewers need to audit together.

Preferred structure serializer groups are:

- `structure/core`: shared helpers, pNext validation/packing, plain scalar
  typed structs, and common pointer-offset recovery rules. Target 20-40
  structs/helpers.
- `structure/instance_device`: instance and device create-info graphs,
  application info, device queue create info, enabled feature chains, and
  extension/layer name arrays. Target 30-60 structs.
- `structure/memory_buffer`: buffer create infos, memory allocation infos,
  memory requirements-style structs, buffer views, and memory/buffer pNext
  structs. Target 25-45 structs.
- `structure/image`: image, image-view, framebuffer attachment, subresource,
  sparse image, and image-memory binding structs. Target 60-90 structs.
- `structure/shader_pipeline`: shader modules, specialization info, pipeline
  layouts, pipeline shader stages, graphics/compute pipeline create-info graphs,
  and pipeline cache structs. Target 70-110 structs when the graph remains
  cohesive.
- `structure/renderpass`: render pass, subpass, attachment, framebuffer, and
  dynamic-rendering structs. Keep render-pass graphs separate from pipeline
  graphs once either group becomes large. Target 30-60 structs.
- `structure/descriptor`: descriptor set layout, descriptor pool, descriptor
  write/copy/update-template, descriptor buffer, and descriptor indexing structs.
  Target 50-80 structs.
- `structure/command_buffer`: command buffer begin/submit/inheritance structs,
  indirect draw/dispatch command structs, and command-buffer recording payload
  structs that are not better owned by image, sync, or descriptor groups. Target
  40-70 structs.
- `structure/sync`: fences, semaphores, events, timeline semaphore, submit/wait,
  dependency, memory barrier, buffer barrier, and image barrier structs. Target
  50-80 structs.
- `structure/query`: query pool, performance query, timestamp, calibrated
  timestamp, and counter structs. Target 25-45 structs.
- `structure/surface_swapchain`: surface capability/format/present mode structs,
  swapchain create/acquire/present structs, and platform surface create infos.
  Target 50-90 structs.
- `structure/debug_tooling`: debug utils, debug report, validation feature,
  marker, label, and object-name/tag structs. Target 20-40 structs.
- `structure/extensions_misc`: extension-family overflow groups when a family is
  too small or too isolated for a dedicated domain group. Target 20-80 structs
  per extension-family bucket.

Target structure group size is about 20-80 structs. Split earlier when one group
contains unrelated pointer graphs or when generated tests become hard to scan.
It is acceptable for small scalar-only structs to share a larger group and for
highly cohesive heavy domains, especially pipeline creation, to grow toward
80-110 structs. Structs with nested arrays, `pNext` payloads, callbacks,
external handles, or platform resources should stay near the code and tests that
document their serialization contract even when that leaves a smaller group.
